# CS265 — Project Requirements & Assessment Checklist

**รายวิชา:** CS265 การพัฒนาโปรแกรมประยุกต์สำหรับอุปกรณ์พกพาเบื้องต้น  
**ปีการศึกษา:** 2569  
**สถานะเอกสาร:** Baseline requirements (อ้างอิงเกณฑ์ที่ผู้ใช้ให้มา ณ 17 พฤศจิกายน 2569)  
**วัตถุประสงค์:** ใช้กำกับการพัฒนาแอปพลิเคชันบนอุปกรณ์พกพา การทดสอบ การเตรียมหลักฐานในรายงาน และการนำเสนอ เพื่อให้ครบเกณฑ์ทั้ง 20 ข้อย่อย

> **ข้อควรแยกให้ออก:** ส่วน **[RUBRIC]** คือข้อกำหนดตามเกณฑ์ที่ได้รับ ส่วน **[GUIDANCE]** เป็นแนวทางปฏิบัติ/ตัวอย่างที่แนะนำ ไม่ใช่ข้อบังคับเพิ่มเติมของรายวิชา  
> เครื่องหมาย `[ ]` หมายถึง **ยังไม่ได้ตรวจรับ/ไม่มีหลักฐานยืนยัน** ไม่ได้แปลว่าแอปทำไม่ได้

## 1. การให้คะแนน

มี **5 หมวด** หมวดละ **4 เกณฑ์ย่อย** รวม **20 เกณฑ์ย่อย**

| จำนวนเกณฑ์ย่อยที่ผ่านในแต่ละหมวด | คะแนนหมวดนั้น |
| ---: | ---: |
| 4 | 4 |
| 3 | 3 |
| 2 | 2 |
| 1 | 1 |

**เป้าหมายการส่งงาน:** ผ่านให้ครบ 20/20 ข้อ เพื่อให้ได้ 4 คะแนนในแต่ละหมวดตาม Rubric (รวม 20 คะแนนจาก 5 หมวด หากแต่ละหมวดมีน้ำหนักเท่ากัน)  
**หมายเหตุ:** เกณฑ์ต้นทางไม่ได้ระบุกรณีที่ผ่าน **0 ข้อ** หรือการถ่วงน้ำหนักหมวด จึงไม่อนุมานคะแนนในกรณีนั้น

## 2. Functional Completeness & Report Evidence — หมวด 1

### REQ-1.1 รายการฟังก์ชันหลักครบถ้วน [RUBRIC]

- [ ] ระบุ **ฟังก์ชันที่จำเป็น** ทุกฟังก์ชันให้ครบตามขอบเขตโครงงาน (Scope/MVP ที่ตกลงกัน)
- [ ] แต่ละฟังก์ชันระบุ **หน้าจอ** ที่ใช้ และ **ผลลัพธ์** ที่ผู้ใช้ได้รับอย่างชัดเจน
- [ ] มีหลักฐานประกอบ เช่น ภาพหน้าจอหรือผลการทำงานจริง

**หลักฐานขั้นต่ำที่ควรจัดเก็บ:** ตาราง `Function ID | ชื่อฟังก์ชัน | หน้าจอ | Input/Action | ผลลัพธ์ | ภาพ/อ้างอิง`  
**วิธีตรวจ:** เทียบรายการฟังก์ชันกับขอบเขตโครงงานและ UI/Build จริง ไม่ให้ฟังก์ชันสำคัญตกหล่น

### REQ-1.2 ทดสอบทุกฟังก์ชันที่จำเป็น [RUBRIC]

- [ ] มีผลทดสอบ **ทุกฟังก์ชันที่จำเป็น** ตาม REQ-1.1
- [ ] แต่ละกรณีทดสอบระบุ **วิธีทดสอบ / ผลที่คาดหวัง / ผลที่ได้จริง**
- [ ] ทดลองแล้วฟังก์ชันทำงานได้ พร้อมหลักฐานผลทดสอบ

**หลักฐานขั้นต่ำที่ควรจัดเก็บ:** ตาราง `Test ID | Function ID | ขั้นตอน | Expected | Actual | Pass/Fail | Evidence`  
**วิธีตรวจ:** ทุก Function ID ที่จำเป็นต้องมีอย่างน้อยหนึ่ง Test ID ที่แสดงผลผ่านจริง

### REQ-1.3 เชื่อมโยงเนื้อหา CS265 [RUBRIC]

- [ ] ระบุแนวคิด/เทคนิคที่นำมาใช้ซึ่งเกี่ยวข้องกับเนื้อหารายวิชา CS265
- [ ] อธิบายว่าเทคนิคนั้นถูกใช้ **ตรงส่วนใด** และ **เพื่ออะไร** ในโครงงาน

**หลักฐานที่แนะนำ:** แผนภาพ, ภาพ UI, code snippet และตาราง `หัวข้อวิชา | ฟังก์ชันที่ใช้ | วิธีประยุกต์`  
**ข้อควรระวัง:** ตรวจว่าหัวข้อที่ยกมาเป็นเนื้อหารายวิชาที่เรียนจริง ไม่อ้างจากการคาดเดา

### REQ-1.4 เชื่อมโยงความรู้จากรายวิชาอื่น [RUBRIC]

- [ ] อธิบายการใช้ความรู้จากอย่างน้อยหนึ่งรายวิชาอื่นนอกเหนือจาก CS265
- [ ] แสดงการเชื่อมโยงกับ implementation จริง ไม่ระบุเพียงชื่อรายวิชา

**ตัวอย่างที่เลือกได้เมื่อเกี่ยวข้องจริง [GUIDANCE]:** Database → การจัดเก็บข้อมูล, Operating Systems → lifecycle/concurrency, Algorithms → ค้นหาและจัดอันดับ, AI → การประมวลผลเสียงหรือ semantic search

## 3. Application Capabilities & Technical Challenge — หมวด 2

### REQ-2.1 อธิบายกลไกฟังก์ชันหลัก [RUBRIC]

- [ ] เลือกอธิบายฟังก์ชันหลัก **อย่างน้อย 1 ฟังก์ชัน**
- [ ] อธิบายการไหลของข้อมูล **ตั้งแต่รับ Input → ประมวลผล → ผลลัพธ์**
- [ ] มี **โค้ดหรือแผนภาพ** ประกอบคำอธิบาย

**หลักฐานที่แนะนำ:** Sequence diagram / flowchart / architecture diagram + code reference  
**ตัวอย่างหน้ารายงานจากตารางที่ได้รับ:** หน้า 4 (ต้องตรวจหลักฐานจริงอีกครั้ง)

### REQ-2.2 ระบุความท้าทายเชิงเทคนิคและสาเหตุ [RUBRIC]

- [ ] ระบุปัญหาทางเทคนิคจริง **อย่างน้อย 1 เรื่อง**
- [ ] ระบุว่าปัญหาเกิดใน **ฟังก์ชันใด** มีอาการอย่างไร และ **เกิดจากอะไร**

**หลักฐานที่แนะนำ:** บันทึก bug, log, ภาพก่อนแก้, ขั้นตอน reproduce  
**ตัวอย่างหน้ารายงานจากตารางที่ได้รับ:** หน้า 7 (ต้องตรวจหลักฐานจริงอีกครั้ง)

### REQ-2.3 อธิบายวิธีแก้ที่ลงมือทำจริง [RUBRIC]

- [ ] เชื่อมโยงวิธีแก้เข้ากับปัญหาใน REQ-2.2 อย่างตรงจุด
- [ ] ระบุว่า **แก้อะไร / ทำไมวิธีนี้จึงแก้สาเหตุ / แก้ที่ส่วนใดของโค้ด**
- [ ] วิธีแก้ต้องถูกนำไปใช้จริงในแอป

**หลักฐานที่แนะนำ:** before/after code, commit/PR หรือชื่อไฟล์และฟังก์ชันที่แก้  
**ตัวอย่างหน้ารายงานจากตารางที่ได้รับ:** หน้า 7 (ต้องตรวจหลักฐานจริงอีกครั้ง)

### REQ-2.4 ผลหลังแก้ปัญหา [RUBRIC]

- [ ] มีภาพหรือผลทดสอบ **หลังแก้ปัญหา REQ-2.3**
- [ ] ระบุผลว่า **เปลี่ยนจากเดิมอย่างไร** และ/หรือ **ตรงตาม Expected หรือไม่**

**หลักฐานที่แนะนำ:** คู่ภาพ Before/After, test output, logs หรือ metrics ที่วัดซ้ำได้

**แม่แบบบันทึกปัญหาเชิงเทคนิค [GUIDANCE]:**

| ช่อง | สิ่งที่ต้องกรอก |
| --- | --- |
| Feature | ชื่อฟังก์ชัน/จุดที่มีปัญหา |
| Problem | อาการและขั้นตอนทำให้เกิดซ้ำ |
| Root cause | วิเคราะห์สาเหตุทางเทคนิค |
| Fix | วิธีแก้และเหตุผลที่เลือก |
| Code reference | ไฟล์ / คลาส / ฟังก์ชัน / commit |
| Before | อาการ/ผลทดสอบก่อนแก้ |
| After | หลักฐานผลหลังแก้ พร้อม Expected/Actual |

## 4. Device & UI Compatibility — หมวด 3

### REQ-3.1 หน้าจอหลายขนาดและความละเอียด [RUBRIC]

- [ ] ทดสอบบน **อย่างน้อย 2 รูปแบบหน้าจอ** ที่ขนาดและความละเอียดแตกต่างกัน
- [ ] หน้าจอหลักแสดงข้อความและปุ่มโดย **ไม่ถูกตัด ไม่ซ้อนกัน**
- [ ] ใช้งานได้จริงบนทั้ง 2 รูปแบบ

**หลักฐานที่ควรจัดเก็บ:** รุ่นอุปกรณ์/emulator, screen size/resolution, ภาพหน้าจอและผลกดใช้งาน  
**แนวทาง [GUIDANCE]:** เลือกมือถือจอเล็กหนึ่งรูปแบบและจอใหญ่/แท็บเล็ตหนึ่งรูปแบบ ตรวจ scrolling, text wrapping และ touch target

### REQ-3.2 Orientation [RUBRIC]

- [ ] เลือกแนวทางและระบุในรายงานให้ชัดเจน:
  - [ ] **ทางเลือก A:** รองรับแนวตั้งและแนวนอน โดยหมุนหน้าจอหลักแล้วเนื้อหา/ปุ่มยังครบและใช้งานได้
  - [ ] **ทางเลือก B:** ตรึงการแสดงผลไว้ในแนวเดียว (Portrait-only หรือ Landscape-only)
- [ ] มีผลทดลองบนอุปกรณ์จริงหรือ emulator ตามทางเลือกที่ใช้

> **สำคัญ:** เกณฑ์อนุญาตการล็อก orientation ไว้แนวเดียว ไม่จำเป็นต้องพัฒนาทั้งสองแนวหากเลือกทางเลือก B

### REQ-3.3 ภาษาไทยและอังกฤษ [RUBRIC]

- [ ] UI มีข้อความ **ภาษาไทยและภาษาอังกฤษ**
- [ ] เปลี่ยนภาษาที่ใช้ทดสอบได้ และเมนู/ปุ่ม/**ข้อความแจ้งเตือนที่แอปสร้างเอง** แสดงตามภาษาที่เลือก
- [ ] มีหลักฐานหน้าจอทั้งสองภาษา

**แนวทาง [GUIDANCE]:** ใช้ string resources (`values/strings.xml`, `values-th/strings.xml`) และหลีกเลี่ยง hardcoded strings ในหน้าจอ  
**ตัวอย่างหน้ารายงานจากตารางที่ได้รับ:** หน้า 2 (ต้องตรวจหลักฐานจริงอีกครั้ง)

### REQ-3.4 Day & Night Theme [RUBRIC]

- [ ] มีทั้ง **Day (Light)** และ **Night (Dark)** theme
- [ ] ทดสอบสลับธีมแล้วหน้าจอหลักเปลี่ยนตามธีม
- [ ] ข้อความอ่านได้ชัด และปุ่มแยกจากพื้นหลังได้ทั้งสองธีม
- [ ] มีภาพหน้าจอสองธีม

**แนวทาง [GUIDANCE]:** ใช้ธีมที่รองรับ Light/Dark ตั้งแต่ต้น; ทดสอบ contrast ของข้อความ บทสนทนา และ dialog

## 5. Navigation, Deletion & Activity Lifecycle — หมวด 4

### REQ-4.1 Back navigation ที่ถูกต้อง [RUBRIC]

- [ ] มีแผนภาพหรือกฎการย้อนกลับของหน้าจอที่เข้าถึงจากเมนู
- [ ] ทดสอบ Back จาก **ทุกหน้าเนื้อหาหลัก** แล้วกลับหน้าก่อนหน้าหรือหน้าที่กำหนดไว้
- [ ] ไม่กระโดดไปหน้าที่ไม่เกี่ยวข้อง

**หลักฐานที่ควรจัดเก็บ:** Navigation graph + ตารางเส้นทาง `Current → Back → Expected destination → Actual destination`

### REQ-4.2 ป้องกันการออกโดยไม่ตั้งใจ [RUBRIC]

- [ ] เมื่อ Back ทำให้ **ออกจากแอป/ออกจากงานที่กำลังทำโดยไม่ตั้งใจ** มีการเตือนให้กดซ้ำสองครั้ง **หรือ** แสดงหน้าต่างยืนยันก่อน
- [ ] ทดสอบกรณี **ยกเลิก** แล้วผู้ใช้ยังอยู่ในงาน/สถานะปัจจุบัน
- [ ] ทดสอบกรณี **ยืนยัน** แล้วเกิดการออก/ย้อนกลับตามที่ออกแบบ

**ข้อแนะนำในการตีความ [GUIDANCE]:** การ Back เพื่อเดินกลับระหว่างหน้าตาม REQ-4.1 ไม่จำเป็นต้องมี dialog ทุกครั้ง แต่จุดที่เสี่ยงออกจากแอปหรือสูญเสียงานที่กำลังทำต้องได้รับการป้องกันและมีหลักฐานทดสอบ

### REQ-4.3 ยืนยันก่อนลบทุกครั้ง [RUBRIC]

- [ ] ทุกจุดที่มีคำสั่ง **ลบข้อมูล** แสดง confirmation ก่อนลบ
- [ ] ทดสอบเลือก **ยกเลิก** → ข้อมูลต้องยังอยู่
- [ ] ทดสอบเลือก **ยืนยัน** → ข้อมูลจึงถูกลบ

**หลักฐานที่ควรจัดเก็บ:** รายการ Delete entry points + ภาพ dialog + ผล Cancel/Confirm แยกกัน  
**สำคัญ:** ต้องทดสอบ **ทุกจุด** ที่ลบได้ ไม่ใช่เฉพาะปุ่มลบของหน้าหลัก

### REQ-4.4 Activity lifecycle / หยุดและทำต่อ [RUBRIC]

- [ ] เมื่อสลับไปใช้แอปอื่น **งานหลักที่กำลังดำเนินอยู่ต้องหยุดตามที่ออกแบบ**
- [ ] เมื่อกลับมา แอปสามารถ **ทำงานต่อจากสถานะเดิม** โดยไม่เริ่มผิดจุดหรือสูญเสีย progress
- [ ] ทดสอบกับงานหลักอย่างน้อยหนึ่งประเภท เช่น timer, เสียง หรือความคืบหน้าของงาน และเก็บหลักฐาน

**แนวทาง [GUIDANCE]:** ออกแบบ lifecycle-aware state; จัดการ pause/resume ของ job, playback หรือ recording ตามพฤติกรรมที่กำหนดและข้อจำกัดระบบ Android; แยกกรณี background กับ process death (อย่างหลังเป็นการทดสอบเสริม ไม่ได้ระบุเป็นเกณฑ์ตรง ๆ)

## 9. โครงรายงานที่แนะนำ [GUIDANCE]

1. **ภาพรวมโครงงาน:** ปัญหา ผู้ใช้เป้าหมาย Scope และรายการฟังก์ชัน (REQ-1.1)
2. **User Flow:** ภาพหน้าจอต่อเนื่องอย่างน้อย 1 เส้นทาง พร้อม action/ผลลัพธ์ (REQ-5.1)
3. **Architecture & Technical Mechanism:** input/process/output, แผนภาพ/โค้ด และการเชื่อมกับ CS265/วิชาอื่น (REQ-2.1, 1.3, 1.4)
4. **Test Results:** ตารางทดสอบทุกฟังก์ชัน + หลักฐานความเข้ากันได้ของอุปกรณ์/ภาษา/ธีม/Back/Delete/Lifecycle (REQ-1.2, 3.*, 4.*)
5. **Technical Challenge:** ปัญหา สาเหตุ วิธีแก้ ตำแหน่งโค้ด และก่อน/หลังแก้ (REQ-2.2–2.4)
6. **Attribution:** ที่มาโค้ด สื่อ เครื่องมือ AI และการแยกส่วนที่พัฒนาเอง (REQ-5.2)
7. **สรุปและข้อจำกัด:** สิ่งที่ทำสำเร็จ สิ่งที่ยังไม่อยู่ใน Scope และสิ่งที่ควรพัฒนาต่อ

## 10. Mobile App Implementation Pointers [GUIDANCE — ไม่ใช่ Rubric]

*ถ้าโครงงานใช้ Android/Kotlin สามารถใช้รายการนี้เป็นแนวปฏิบัติ แต่เกณฑ์รายวิชาไม่ได้บังคับ Library/Framework รายตัว*

| ความต้องการ | ทางเลือก implementation |
| --- | --- |
| รองรับหลายหน้าจอ (3.1) | Compose responsive/adaptive layout, `BoxWithConstraints` หรือ resource qualifiers |
| Orientation (3.2) | ตรวจ configuration changes, state retention หรือกำหนด portrait lock เมื่อเลือกแบบนั้น |
| ภาษา TH/EN (3.3) | Android localized resources; ครอบคลุม snackbar, validation, dialog |
| Day/Night (3.4) | Material 3 theme + light/dark color scheme |
| Back navigation (4.1–4.2) | Navigation Compose, `BackHandler`, back stack ที่กำหนดชัดเจน |
| Confirm deletion (4.3) | `AlertDialog` / confirmation bottom sheet ที่ทุก delete entry point |
| Lifecycle (4.4) | `Lifecycle`/`ViewModel`, save state และ pause/resume งานแบบ lifecycle-aware |
| ทดสอบและเก็บหลักฐาน (1.2) | Manual test sheet, Compose UI test, unit test, Logcat และ screenshots |

### ตัวอย่างการผูกกับแอปจดโน้ตด้วยเสียง (ถ้าเป็นขอบเขตโครงงานที่เลือก) [GUIDANCE]

- **Main flow:** เปิดแอป → เริ่มพูด/บันทึก → ดูข้อความที่ถอดเสียง → แก้ไข → บันทึกโน้ต → เปิดอ่านโน้ต
- **REQ-1.1/1.2:** ทำ Function Matrix และ Test Cases ของ Record/STT, Note CRUD, Copy และ Search **เฉพาะฟังก์ชันที่อยู่ใน Scope จริง**
- **REQ-2.1:** อธิบาย Speech input → Speech recognition → Draft transcript → User review → Note persistence
- **REQ-2.2–2.4:** เลือกปัญหาที่พบจริง เช่น STT หยุดเมื่อย้ายแอป, สถานะ recording หลังหมุนจอ หรือ async result race; อย่าสร้างปัญหาสมมติเพียงเพื่อกรอกรายงาน
- **REQ-4.2:** ระหว่างบันทึก/แก้ draft ต้องไม่ทำให้ข้อมูลหายเพราะกด Back ผิด
- **REQ-4.3:** ลบ Note ทุกจุดต้องมี confirmation
- **REQ-4.4:** ทดสอบการหยุด STT/recording เมื่อ background และ resume อย่างมี state ตรงตามพฤติกรรมที่ออกแบบ โดยเคารพข้อจำกัด microphone/privacy ของ Android
